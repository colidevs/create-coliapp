# Customize this store

This template ships with **generic placeholders**, not a working store. Nothing here is
speculative — every field, env var, and command below is read directly from this project's
own source, not copied from an older audit. Walk the user through the 8 steps below, in
order, asking one question at a time and acting on the answer before moving to the next step.

**Read `apps/api/src/config.ts` (the `envSchema` export) and `apps/web/src/env.ts` yourself
before starting** if this file is more than a few weeks old relative to the project — those
two files are the authoritative source for every required env var, not this list. This skill
mirrors them at the time it was written; if they've drifted, trust the code.

## Before you start: architecture in one paragraph

`apps/api` (Express, port `3001` by default) owns the database and all business logic.
`apps/web` (Next.js, port `3000`) is a thin client — it never talks to Postgres directly. A
**product** is catalog metadata only (name, slug, description, images); price/stock/SKU live
on its **variants**. **Variant option types** (e.g. "Size", "Color") and their **option
values** (e.g. "S"/"M"/"L", "Red"/"Blue") are rows an admin creates through the admin UI or
API — never a migration or a code change. This is the whole point of the variants redesign:
a clothing store and a pet-products store both use the same schema, they just seed different
option-type data.

**Scope note — this vs. colidevs-standard's design-time guidance**: some of what's below
(payment config, deployment env vars) resembles what `coli-marketplace`'s
`api-standard-design`/`frontend-standard-design` skills already surface as design constraints
for a **brand-new** feature, before any code exists. This skill runs at a different moment:
**after** a project has already been scaffolded from this template, walking through setting up
a real, already-generated instance for a real client. Same underlying standard, a genuinely
different phase — this is post-scaffold configuration, not a duplicate of design-time guidance.

## Step 1 — Confirm branding basics

The store name is already substituted at scaffold time via `{{name}}` wherever it appears in
code (`apps/web/src/config/site.ts`, `package.json` names, etc.) — confirm with the user that
substitution actually took the right value, then ask what still needs manual attention, since
substitution does **not** touch:

- `apps/web/src/config/site.ts` — the branding object:
  ```ts
  export const siteConfig = {
    name: "{{name}}",
    url: "https://{{name}}.colidevs.com",
    ogImage: "https://{{name}}.colidevs.com/og.jpg",
    description: "{{name}} generated by create-coliapp",
    links: {
      instagram: "https://instagram.com/colidevs",
    },
  };
  ```
  - `url`/`ogImage` almost certainly need a real production domain, not the `*.colidevs.com`
    placeholder, unless this client is genuinely hosted under a colidevs subdomain.
  - `description` reads as scaffold boilerplate ("generated by create-coliapp") — ask for real
    marketing copy.
  - **`links.instagram` is hardcoded to colidevs' own account** (`https://instagram.com/colidevs`),
    not a placeholder. Ask for the client's real Instagram (or drop it) — do not ship this as-is.
    There is no other social link field (no Twitter/Facebook/TikTok) — if the client wants more,
    that's a small code change to `SiteConfig`, not just data entry.
- The two `LICENSE` files (`apps/api/LICENSE` = Apache-2.0, `apps/web/LICENSE` = MIT) — confirm
  these are still correct for this specific engagement.

**Before asking about colors, typography, or tone of voice**: ask the user whether they have
real visual references for this client — screenshots, competitor sites, a brand manual, mood
boards, or specific inspiration links (e.g. a client sending over a competitor's storefront or a
brand's own site as a look-and-feel target). If they do, this is a design-to-code task, and the
real risk is a *shallow* match — one that copies the reference's colors/fonts while leaving the
page's actual structure untouched. Two ways this concretely went wrong on a real client pilot
before landing on the process below: (1) treating "apply the visual direction" as a palette+
typography swap only, never touching layout/component structure at all; (2) rebuilding structure
from an AI-paraphrased description of the reference instead of the reference itself — a
paraphrase is already one lossy step removed from the real site and loses exactly the structural
detail that matters.

The process that actually worked, in order:

1. **Structure first, theme second — two separate passes, never one.** Map layout, section
   order, and component composition from the reference *before* touching any color or font.
   Confirm that structural pass is right before starting the theme pass.
2. **Ground the structural read in the real reference, never a summary of it.** Take real
   screenshots of the reference site(s) (Playwright, or ask the user for screenshots) and/or
   inspect their real DOM. Do not work from a prose description of the reference — treat any
   such summary as unusable for structural decisions, no matter how detailed.
3. **When more than one reference is given, confirm which is the primary structural target
   before starting.** Do not blend two sites' structures into an invented composite — ask which
   reference's structure wins if they conflict.
4. **Audit shared-component-library adoption for completeness, not just first use.** If this
   store's admin uses `@colidevs/ui` components, check every touched form/page uses them
   consistently — not only the first one you happened to update (see the Step 6 gotcha below for
   a concrete case this exact template hit).
5. **Verify with a fresh pass that didn't build it.** Compare the result against the real
   reference screenshots from a context that didn't do the implementation (a fresh agent, or the
   user) — whoever built it is the worst judge of whether it actually matches.

Only fall back to asking the user to describe colors/fonts/tone directly in prose when no visual
references exist at all.

## Step 2 — Business category and initial variant option types

Ask what kind of store this is, then propose a starting set of option types. Do not require a
migration for this — it's plain data. Examples to offer, adjust to the actual business:

| Business type | Suggested option types → values |
|---|---|
| Clothing / apparel | Size → S, M, L, XL · Color → Black, White, Red, Blue |
| Pet products | Size → Small, Medium, Large · Material → Cotton, Nylon |
| Footwear | Size → 36–45 (EU) · Color → ... |
| Electronics/accessories | Color → ... · Storage/Capacity → ... |

**These are created after Step 4 (the database is running)** — creation happens either through
the admin UI or the admin API, never a schema change:

- Admin UI: `/admin/variant-option-types/add` to create a type (e.g. "Size"), then
  `/admin/variant-option-values/add` per value, picking that type. List views live at
  `/admin/variant-option-types` and `/admin/variant-option-values`.
- Admin API (for scripting several at once — needs a logged-in admin session cookie *and* the
  `x-service-key` header, see Step 4's checklist):
  ```
  POST /api/v1/admin/variant-option-types      { "name": "Size", "displayOrder": 0 }
  POST /api/v1/admin/variant-option-values     { "optionTypeId": "<uuid from above>", "value": "M", "displayOrder": 1 }
  ```
  `slug` is derived server-side from `name`/`value` — never send it yourself.

Then, per product, an admin creates one or more variants under
`/admin/products/<id>/variants/add`, each variant picking one value per option type it applies
to, plus its own `price`/`stock`/`code`. A product itself carries no price/stock at all — it
starts as a draft (`isPublished: false`) and can only be published once it has at least one
active variant (enforced by a database trigger, not just UI validation). `isPublished` is the
draft/published flag; `isActive` is a separate, product-level soft-delete flag — don't conflate
the two, they used to be the same boolean and that was a real bug.

## Step 3 — Payment provider (dLocal)

**Set every env var in this step (and Steps 4-5) through Infisical, not a hand-edited `.env`
file.** Per hefesto's `.claude/rules/secrets-management.md` local-dev convention:

1. Run `infisical init` once, against this client's real Infisical project — this creates and
   commits `.infisical.json` (safe to commit: it holds only the Project ID, never secret
   values).
2. Both `apps/api/package.json` and `apps/web/package.json` already ship a single,
   Infisical-wrapped `dev` script (`infisical run --env=dev --path=/api -- ...` and
   `--path=/web` respectively) — there is no separate plain `dev` variant to fall back to.
   Confirm both still match this shape; if either was hand-edited back to a bare command, fix it
   before proceeding.
3. Populate the Infisical project's `dev` environment at `/api` with every var listed in
   `apps/api/.env.example` (that file mirrors `src/config.ts`'s `envSchema` exactly — trust it
   over this prose if they ever drift), and at `/web` with `apps/web/.env.example`'s 4 vars.
   `.env.example` files are documentation only — they are never read at runtime once Infisical
   is wired.

The table below explains the 8 dLocal-specific vars from that list in plain language:

| Var | What it is |
|---|---|
| `DLOCAL_API_URL` | dLocal's API base URL — **sandbox** (`https://sandbox.dlocal.com`) while testing, the **production** URL only once the client has a live dLocal merchant account approved. |
| `DLOCAL_API_KEY` | dLocal's public/login key for this merchant account. |
| `DLOCAL_API_SECRET` | dLocal's secret key — pairs with the key above to sign requests. Never commit this or log it. |
| `DLOCAL_NOTIFICATION_URL` | Where dLocal POSTs async payment-status webhooks. **Must be a publicly-reachable HTTPS URL** — `http://localhost:...` will never receive anything from dLocal's servers. If testing locally, use a tunnel (e.g. `ngrok`/Cloudflare Tunnel) and point this at the tunnel's public URL + the webhook route. |
| `DLOCAL_SUCCESS_URL` | Where the buyer's browser is redirected after a successful payment. Public-facing, e.g. `https://<store-domain>/checkout/success`. |
| `DLOCAL_BACK_URL` | Where the buyer is sent if they cancel/back out of payment. |
| `DLOCAL_DEFAULT_CURRENCY` | 3-letter ISO code (e.g. `ARS`, `USD`, `MXN`) — must match what the client's dLocal account is configured to settle in. |
| `DLOCAL_DEFAULT_COUNTRY` | 2-letter ISO country code (e.g. `AR`, `MX`, `CO`) — must match the buyer's country dLocal expects for this integration. |

Ask the client (or the person setting this up) for their real dLocal sandbox credentials first
— get checkout working end-to-end against sandbox before ever touching production values.

## Step 4 — Database setup

This is a hard sequence — each step depends on the one before it. Full detail lives in
`apps/api/drizzle/MIGRATIONS.md`; this is the actionable summary:

1. **Bootstrap roles** (once, as a Postgres superuser — never as part of normal app startup):
   ```sh
   psql "postgres://<superuser>@<host>:5432/<db>" -f apps/api/drizzle/bootstrap-roles.sql
   ```
   This creates exactly three roles: `app_owner` (`NOLOGIN`, owns every table), `app_migrator`
   (`LOGIN`, member of `app_owner`, CI/deploy-exclusive — this is the role migrations run as),
   `app_runtime` (`LOGIN`, `NOBYPASSRLS` — this is the role the running app connects as). It also
   grants `CREATE` on the database/schema to `app_owner`. It's idempotent (`IF NOT EXISTS`
   guarded), so re-running it is safe. **Change the placeholder passwords** it sets
   (`change_me_in_infisical`) before this touches anything but a local throwaway database.

2. **Run migrations**, connected as `app_migrator` via `DATABASE_OWNER_URL`:
   ```sh
   pnpm --filter ./apps/api db:migrate
   ```
   This applies, in order: `0000_init.sql` → `0001_rls_roles.sql` →
   `0002_better_auth_core_tables.sql` → `0003_better_auth_organization_tables.sql` →
   `0004_chubby_nico_minoru.sql` (creates the variants/option-type/option-value/selection
   tables) → `0005_variant_rls_and_invariants.sql` (RLS + the "a product needs ≥1 active
   variant" trigger).

3. **There is no seed script.** Confirmed — no `db:seed` command anywhere in this template, no
   `INSERT` statements in any migration. After migrating, the database is structurally ready
   but has zero categories/products/option-types. Populate it either through the admin UI, or by
   scripting calls against the admin API (Step 2 above) — there is no shortcut.

4. **Create the first admin user.** There is no sign-up page in the UI (`apps/web`'s login form
   at `/auth/login` only signs in, it never signs up) — create the account directly against
   Better Auth's own API once `apps/api` is running:
   ```sh
   curl -X POST "$BETTER_AUTH_URL/api/auth/sign-up/email" \
     -H "Content-Type: application/json" \
     -d '{"email":"admin@example.com","password":"<strong password>","name":"Admin"}'
   ```
   **Important, worth flagging to whoever reviews this template next**: `apps/api/src/lib/ability.ts`'s
   `resolveRole()` currently ignores the session entirely and unconditionally returns `"admin"`
   — every signed-in user is an admin today, there is no `"viewer"` role reachable in practice
   yet. Fine for a single-admin client site; do not rely on this for a multi-user permission
   split without fixing `resolveRole()` first.

## Step 5 — Deployment-specific values

- `CORS_ALLOWED_ORIGINS` (`apps/api`) — comma-separated list of origins allowed to call the API.
  Must include wherever `apps/web` is actually served from (its real domain in production, or
  `http://localhost:3000` — see the footgun below — in dev).
- `API_BASE_URL` / `NEXT_PUBLIC_API_BASE_URL` (`apps/web`) — **both must point at wherever the
  browser can actually reach the API, never a bare `localhost` if you're testing from a phone,
  another machine, or any device other than the one running `apps/api`.** `localhost` from a
  different device resolves to *that device itself*, not your API server — this is the single
  most common "it works on my machine but the storefront shows nothing" bug. Use the host
  machine's real LAN IP or a tunnel URL in that case.
- `SERVICE_KEY` **must be the identical value on both sides** — `apps/web` sends it as the
  `x-service-key` header on every request to `apps/api`; `apps/api`'s own `SERVICE_KEY` is what
  it checks that header against. A mismatch here fails every request from the storefront/admin
  UI to the API, silently from the browser's point of view (it just looks like every page is
  broken).
- `BETTER_AUTH_URL` must be the API's own public URL (matches where `/api/auth/*` is actually
  reachable) — this is what dLocal's redirect and any auth-adjacent flow resolves against too.

## Step 6 — Branding assets

- **Logo/favicon**: not covered by any env var — these are static files under `apps/web/public`
  (or wherever Next's metadata/icon convention points); replace them directly.
- **Image hosting domain**: `apps/web/next.config.ts` only allows one remote image host today:
  ```ts
  images: {
    unoptimized: true,
    remotePatterns: [{ protocol: "https", hostname: "images.colidevs.com" }],
  },
  ```
  If this client's product images are served from anywhere else, add that hostname here or
  every `next/image` render for those images will fail. `unoptimized: true` is intentional
  (this host is already a Thumbor-fronted image service doing its own resizing) — don't remove
  it without understanding why it's there (`.claude/rules/frontend-performance-tooling.md` in
  hefesto, if available).
- **Social links**: see Step 1 — only `links.instagram` exists on `SiteConfig` today.
- **`@colidevs/ui` components need an explicit Tailwind `@source` glob, or they render broken.**
  `@colidevs/ui` (used for form fields, `Switch`, etc.) ships pre-built component output under
  `node_modules` — Tailwind v4's automatic content detection never scans `node_modules`, so any
  utility class used only inside that package's compiled files silently never gets generated.
  Confirmed live: `Switch`'s `w-8` track width was missing, and the switch rendered as a bare
  circle instead of a pill with a track. Fix: `apps/web/src/styles/globals.css` must carry
  `@source "../../node_modules/@colidevs/ui/dist/**/*.{js,jsx,ts,tsx}";` right after
  `@import "tailwindcss";` — confirm it's still there if any `@colidevs/ui` component looks
  visually broken (unstyled, wrong size, missing background) despite working correctly
  functionally.

## Step 7 — Standard content pages (Terms, Privacy, FAQ, About)

This template ships four real, reachable storefront routes —
`(ecommerce)/{terms,privacy,faq,about}/page.tsx`, linked from the footer — but every one of them
ships **placeholder content only**. `/terms` and `/privacy` carry a visible `PlaceholderNotice`
banner; `/faq` and `/about` mark their placeholder text inline. **None of the four is ready for
a real client launch as-is.**

- `/terms` (Terms & Conditions) is not optional decoration: dLocal (this template's payment
  provider) requires a merchant-facing Terms & Conditions page for compliance. The page
  *existing* satisfies that structural requirement — the actual legal text is the client's (or
  their lawyer's) responsibility. Never invent real legal language yourself.
- `/privacy` (Privacy Policy) — same posture: the route exists, the real text does not, and
  supplying it is the client's own responsibility.
- `/faq` and `/about` carry no compliance stakes, but shipping visible `[Placeholder]` text on a
  live client site is a real credibility problem, not a cosmetic one.

Ask the client for real Terms/Privacy text (or get an explicit commitment that it lands before
launch) and real FAQ/About copy, then replace each page's placeholder sections directly — this
is content editing inside an existing route, never a schema, routing, or code change.

## Step 8 — Ready checklist

Confirm all of the following before handing this off:

1. `GET {API_BASE_URL}/health` → `200` (process is up; no dependency checks).
2. `GET {API_BASE_URL}/ready` → `200` (DB and other dependencies are actually reachable).
3. Sign in at `apps/web`'s `/auth/login` with the admin account created in Step 4 — lands on
   `/admin`.
4. At least one variant option type + its values are visible under `/admin/variant-option-types`
   and `/admin/variant-option-values`.
5. At least one product with at least one **active** variant exists and is published
   (`isPublished: true` on the product) — try publishing a product with zero active variants and
   confirm it's rejected (the DB trigger from migration `0005` should reject it with a 422).
6. The storefront shows that product, a variant selector renders, and picking a combination
   updates the displayed price/stock.
7. Add-to-cart → checkout completes a full dLocal **sandbox** payment and the resulting order
   shows up under `/admin` orders.
8. If dLocal notifications are involved, confirm `DLOCAL_NOTIFICATION_URL` is actually reachable
   from the public internet (not just from your machine) — a local tunnel that expired between
   setup and testing is a common false-pass here.
9. `/terms`, `/privacy`, `/faq`, and `/about` carry the client's real content, not the shipped
   `PlaceholderNotice`/`[Placeholder]` text (see Step 7).
